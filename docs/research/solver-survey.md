# R1 — Solver landscape and integration gate

Research date: 2026-11-02 local; maintenance metadata refreshed 2026-11-03 02:58 UTC (still November 2 local). **Provisional survey, not an integration approval or verification report.** All Appendix A names are covered below. Links point to primary repositories, manuals, papers or vendor product pages inspected during this research. `U` means latest release/commit date was not exposed or independently established; it is not evidence of abandonment. Web crawl dates and copyright years are not maintenance dates. Commit links below pin maintenance observations, not the versions used in spikes or a complete license audit. Tested dependency pins and transitive license audits remain required before adoption. Where only GitHub's license classification was available, this is explicitly a license-family observation, not proof of an `-only`/`-or-later` grant.

Decision codes: **I?** integration candidate, gated by the five §0.2 conditions; **R** optional external test reference; **S** algorithm/UX study only; **X** no runtime dependency. No candidate has passed all five gates in this survey. “Accuracy evidence” identifies upstream evidence or the benchmark we must run, never a claim that HeaviSolve passed it. No comparative speed measurements were collected.

## Maintenance evidence and its limits

The [stored GitHub commit metadata](../../verification/results/r1-maintenance/github-commits.json) records 41 default-branch heads, their actual committer and author timestamps, subjects and exact source links. This uses the commit endpoint, not repository `pushed_at`, crawl dates or copyright years. A recent head may be documentation, dependency automation or a merge; it is evidence of repository activity, not proof of sustained numerical maintenance or a stable supported API. Author and committer dates can differ. No claim is made that these are the newest commits across every branch.

[Supplementary primary metadata](../../verification/results/r1-maintenance/additional-metadata.json) confirms releases MFEM 4.10 on 2026-09-01, Palace 0.18.1 on 2026-09-21 and QuTiP 5.3.1 on 2026-08-04. Clipper2 and Strawberry Fields are currently archived. The archive API does not expose an archive date, so no date is asserted. A recent commit before archival does not satisfy an ongoing-maintenance adoption argument.

The surveyed original OpenVAF repository has a 2023-10-30 default-branch head. The actual S3 compiler came from [OpenVAF-Reloaded v24.0.2mob, released 2026-08-25](https://github.com/OpenVAF/OpenVAF-Reloaded/releases/tag/v24.0.2mob), whose [observed head](https://github.com/OpenVAF/OpenVAF-Reloaded/commit/2b5909bccd17b1cdc01a3ebced8ca7b3833c8a5c) is dated 2026-11-02. Treat this as a distinct maintained compiler candidate, with its own license/toolchain audit, rather than crediting the original repository with the fork's activity.

MFEM, Netgen, KLayout, ngspice and Xyce have recent source/release evidence within the plan's approximate 12-month window. Gmsh has a March 2026 release. This supports only the recency part of the integration rubric; stable embedding, benchmark CI, lossless mapping and transitive licensing are separate gates. KLayout has measured local geometry preservation; gdstk's SiEPIC metadata conversion does not pass lossless mapping (S6). The archived Clipper2 smoke test is not an approval to adopt it; prefer KLayout booleans unless an ADR establishes a maintained alternative or explicitly accepts a deviation.

Older observed heads include S4 and scuff-em (2018), ITensor C++ and ceviche (2023), EMopt and SQcircuit (2024), and Simphony (2025-10-28, just outside a strict 12-month cutoff). These remain studies or optional references, not maintained integration candidates. Strawberry Fields' latest head concerns cloud decommissioning and its repository is archived; preserve it only as a pinned optional reference, with alternatives such as Piquasso/Perceval evaluated independently. Proprietary-product and non-GitHub `U` entries below remain explicitly unresolved where no authoritative timestamp was retrieved; none is an incorporation candidate.

## Efficiency/accuracy recommendations

| Problem class | Recommendation and reason | Required check |
|---|---|---|
| Straight cross sections, ports, couplers | Mixed edge/nodal FEM at L1; use mode overlap/CMT or EME for long propagation | VER-WG-01/02/04, convergence, spurious-mode rejection |
| Thin metal gaps, curved 3D structures, BEOL | Custom high-order FEM on candidate MFEM infrastructure; conformal geometry avoids uniform-grid feature-resolution cost | Cavity, Mie, SPP, energy balance; no blanket claim FEM always wins |
| Broadband radiation/transients | Meep/openEMS external FDTD references; useful independent discretization | Mesh/time convergence and identical source/boundary conventions |
| Periodic planar layers | RCWA/S4 external reference, analytic transfer matrices first | Diffraction-order convergence and VER-EM-04 |
| Homogeneous-domain nanoparticles | Analytic Mie first; BEM study/reference for surfaces | Material conventions and discretization convergence |
| Large optical networks | Native C++ compact/S-matrix network layer; SAX/Simphony reference conventions | VER-PIC-01…05, passivity and reciprocity |
| Electrical circuits and RF | Existing ngspice and Xyce candidates; no custom SPICE | R6/S3 measurements determine engine status |
| Small open quantum systems | C++ Lindblad/trajectory implementation with QuTiP reference | VER-QO-01/02/06; positivity and trace |
| Linear quantum optics | Separate Fock and Gaussian representations; Perceval and Strawberry Fields/Walrus references | HOM, loss and covariance invariants |
| Circuit quantization | FEM EPR with Palace/scqubits reference | VER-QO-07 |

These are method-selection hypotheses based on scope and dimensionality, not measured rankings. L0 oracles remain independent of production solvers.
